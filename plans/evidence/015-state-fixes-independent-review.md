## Disposition of the three findings

1. **Catalog mutation before admission — resolved.** `extensions/lib/provider.ts:178-193` checks and reserves the runner operation before bridge startup, image-root awaits or catalog/handler mutation. A resumed operation retains this reservation despite not holding the directory lock. Rejection at line 181 occurs outside the new operation's catch/release block, so a competing start cannot release or mutate the owner. `owned.assertValid()` also prevents an operation cancelled during startup from subsequently installing its catalog. The actual bridge mutations are at lines 202-209. The two integration cases at `tests/provider.test.ts:1415-1440` exercise both changed names and changed Pi mappings through the default runner, list the surviving catalog, make a second MCP call and verify the resulting Pi tool identity and unchanged spawn count.

2. **Orphan before suspension publication — resolved.** The ownership latch exists before the child starts. The orphan hook calls `release(owned, error)` (`provider.ts:195-200`), which records failure even when there is no published suspension yet (`158-166`). `finishPhase()` checks it before returning the parked phase (`168-173`). If abandonment instead occurs after that return while the directory lock is being released, the stream's second assertion at line 787 catches it before publication. The validity check and `suspendedByDir.set()` at lines 787-791 contain no intervening await, and publication now precedes the shadow-tool events. On failure before publication, the stream retains its image cleanup ownership and reaches its error cleanup; after publication, release removes only the matching owned suspension. The three integration cases at `tests/provider.test.ts:1443-1471` inject abort, child close and child error immediately after park acceptance, assert no shadow tool publication, check the error outcome, wait for image cleanup and inspect the original driver.

3. **Unpolled terminal escalation retention — resolved.** The runner records accepted call IDs on the owning operation before `notifyPark()` (`provider.ts:203-208`). Terminal success goes through `finishPhase()`/`release()`, and terminal failure through the resume catch/release path (`168-173,238-249`). Both discard that operation's IDs. `discardParks()` removes park resolvers and session ownership, settles any outstanding HTTP request and deletes the corresponding escalation payload (`extensions/lib/provider-mcp.ts:664-676`). Calling the resolver before deleting the escalation is correct here: an escalated resolver can write a final result into the map, and the following deletion removes it. The success/failure integration cases at `tests/provider.test.ts:1474-1493` assert pending results drop from one to zero without polling. The ordinary live-poll test at lines 1498-1518 verifies that output remains pollable while the operation is still running; cleanup is not moved prematurely to tool-result delivery.

## Additional lifecycle checks

- **Stale cancellation:** the stream passes the prior ownership token on both error cancellation and abandoned-transcript cancellation (`provider.ts:712,729`). `runner.cancel()` compares token identity before touching the driver or bridge (`252-257`). An old token cannot cancel a newer operation. A stale delivery is rejected against the current operation's accepted IDs before entering the catch block that releases that operation (`230-238`). A late `release(oldOwned, ...)` cannot clear a newer reservation or suspension: both updates use identity checks (`160,163`). Its bridge discard uses old operation IDs. Untokened explicit cancellation continues to target the current operation by design. This conclusion is from source tracing; I did not run a separate stale-token probe.
- **Terminal delivery and abandonment:** the driver still retains authoritative success/failure while parked and consumes the pending terminal before checking ordinary suspension state or an already-aborted continuation signal (`provider-driver.ts:278-289`). Consumption clears the suspension deadline and active ownership and arms idle reaping. Transport close/error after a retained terminal does not replace it. The new runner latch stays valid through retained-terminal waiting and is released on consumption or explicit abandonment. No new loss of a terminal result was established in the production caller paths.
- **Exact-once orphan handling:** first/subsequent suspended abort, error, close and shutdown still converge on the driver's identity-guarded abandonment. Marker clearing precedes the callback; repeated teardown does not produce another orphan callback for the released turn. Runner release can be reached more than once during error unwinding, but its ID-based discard and ownership checks make cleanup repeat-safe.
- **Locks:** `resume()` contains no `withDirLock()` or lock acquisition (`provider.ts:227-250`). Initial turns retain existing workspace serialization. The operation reservation is checked synchronously rather than awaited, so it adds no dependency cycle with a lock-holding Pi tool. No new lock deadlock was found.
- **Timers, signals and live-child reuse:** the two tests at `tests/provider-driver.test.ts:632-679` keep the child alive after retained SUCCESS/FAILED, observe actual `clearTimeout` on the captured suspension handle, begin a successor, invoke the obsolete deadline and abort the old signal, assert no kill, assert exactly one spawn and one reuse, then complete the successor through that same child. SUCCESS also supplies the bound conversation ID on reuse. These address the earlier timer-consumption and live-child coverage limits directly. No introduced profile or generation regression was found.
